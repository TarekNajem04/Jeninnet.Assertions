# الفصل ١١ — المدقِّقات Validators: توكيدات بلا رمي استثناء

التوكيدات مصمَّمة للرمي. هذا بالضبط ما نحتاجه في الاختبارات، وهو بالضبط ما لا تحتاجه خدمة تعمل في الإنتاج. يحوِّل هذا الباب نفس الأفعال الانسيابية إلى محرّك تحقُّق لرمز الإنتاج — بلا واجهة ثانية وبلا منطق مكرَّر.

والسؤال الذي يطرح نفسه: لماذا نريد قواعد التحقُّق نفسها في الاختبارات والإنتاج أصلًا؟ لأن كليهما يجيب عن السؤال ذاته: هل هذا الطلب سليم؟ الفرق في المصير لا في السؤال؛ فاختبار الطلب المرفوض يريد أن يرى الفشل ظاهرًا، وخدمة الإنتاج تريد أن تراه مُصنَّفًا وقابلًا للتسجيل. ولو كُتبت القواعد مرتين — نسخة ترمي في الاختبارات ونسخة تُرجع في الإنتاج — لانفصلت النسختان مع أول تعديل، ولصارت الرسائل التي يقرؤها الفريق في الاختبار لا تشبه الرسائل التي تُسجَّل في الإنتاج. توحيد الأفعال هو تصحيح لهذا الانفصال، لا مجرد توفير.

## 11.1 المشكلة

لنقل إن نقطة دفع يجب أن ترفض طلبًا غير سليم:

<div dir="ltr">

```csharp
if (order.Total <= 0) { return BadRequest("total must be positive"); }
if (order.Customer is null) { return BadRequest("customer is required"); }
if (order.Items.Count == 0) { return BadRequest("items cannot be empty"); }
```

</div>

ثلاثة <code dir="ltr">if</code> مكتوبة يدويًّا، ورسائل مكتوبة يدويًّا، ولا اتساق مع رسائل الفشل التي يقرؤها الفريق في الاختبارات. المكتبة تملك الأفعال أصلًا — <code dir="ltr">BeGreaterThan(0)</code> و<code dir="ltr">NotBeNull()</code> و<code dir="ltr">NotBeEmpty()</code> — وتنتج رسائل فشل دقيقة الصياغة. المفقود فقط: أنها لا ترمي.

والمشكلة ليست في الأسطر الثلاثة بذاتها، بل في ما تجرُّه معها. كل شرط جديد يُضيف <code dir="ltr">if</code> ورسالة؛ وكل رسالة تُكتب بلغة ثانية، فتنحرف صياغتها عن صياغة التوكيد؛ ثم يبدأ أحدهم في الترجمة أو توحيد المفردات في نسخة واحدة دون الأخرى. بعد أشهر تصير عندك قائمتان من القواعد: واحدة تُصادق عليها الاختبارات، وأخرى تُنفَّذ في الإنتاج، ولا شيء يضمن أنهما الشيء نفسه. المدقِّق يحل المشكلة من جذرها: القاعدة تُكتب مرة واحدة، وتُنفَّذ في الموضعين.

## 11.2 جمع نتيجة

يُنفِّذ <code dir="ltr">AssertionResult</code> كتلة من التوكيدات العادية ويعيد نتيجة بدل رمي استثناء:

<div dir="ltr">

```csharp
var result = AssertionResult.Create(() => {
    order.Total.Should().BeGreaterThan(0);
    order.Customer.Should().NotBeNull();
    order.Items.Should().NotBeEmpty();
});

if (!result.IsSuccess) {
    return BadRequest(result.ToReportJson());
}
```

</div>

كل توكيد في الكتلة يُقيَّم؛ وتُجمَع الإخفاقات بدل التوقّف عند أولها. يكون <code dir="ltr">IsSuccess</code> صحيحًا فقط إذا لم تُنتج الكتلة أي إخفاق. الأفعال الداخلية هي نفسها أفعال <code dir="ltr">Should()</code> المستخدمة في الاختبارات — فلا توجد واجهة تحقُّق موازية يجب تعلمها.

وشرط الاستقلال الذي تعرَّفناه في النطاقات يسري هنا كما هو: اجمع الشروط المستقلة، وأبقِ التابع متسلسلًا. والفرق أن المدقِّق يُرجع النتيجة بدل أن يرميها، فتصبح عندك لائحة إخفاقات كاملة تصلح أن تُعاد إلى العميل: كل عيب في الطلب مع رسالته الخاصة، في طلب واحد، بدل رسالة عامة تُخبر المستخدم أنه أرسل شيئًا خاطئًا ثم تتركه يخمّن.

أما التدفقات اللاتزامنية فتجدها في <code dir="ltr">CreateAsync</code>:

<div dir="ltr">

```csharp
var result = await AssertionResult.CreateAsync(async () => {
    var quote = await pricing.QuoteAsync(order);
    quote.Total.Should().BeGreaterThan(0);
    quote.Currency.Should().Be("USD");
});
```

</div>

## 11.3 الفحص والتقرير

كل إخفاق مُجمَّع هو <code dir="ltr">AssertionFailure</code> هيكلي:

<div dir="ltr">

```csharp
foreach (var failure in result.Failures) {
    Console.WriteLine($"{failure.Expression} ({failure.Category}): {failure.Message}");
}
```

</div>

يحمل كل إخفاق تعبير الموضوع <code dir="ltr">expression</code> والفئة <code dir="ltr">category</code> (اسم فئة التوكيد المُبلِّغة) والرسالة المنسَّقة <code dir="ltr">message</code>، ومعها قيمتا <code dir="ltr">actual</code> و<code dir="ltr">expected</code> حيث يتيح الفعلُ ذلك.

ووجود الحقول منفصلة هو ما يجعل النتيجة قابلة للبرمجة لا للقراءة فقط: يستطيع كود الإنتاج أن يُوجِّه الإخفاقات بحسب فئتها — رفض ٤٠٠ لأخطاء الإدخال، وتسجيل تحذيري لأخطاء التوقُّع — دون أن يفكك نص الرسالة أبدًا. الرسالة للعين، والحقول للكود.

وهناك مساران من نتيجة المُدقِّق إلى باقي المكتبة:

- <code dir="ltr">result.ToReportJson()</code> يسلسل الإخفاقات إلى JSON (<code dir="ltr">count</code> مع مصفوفة <code dir="ltr">failures</code>) للسجلات أو لوحات المؤشرات أو ملحقات CI، بنفس شكل <code dir="ltr">SoftAssertions.ToReportJson()</code>.
- <code dir="ltr">result.ThrowIfFailed()</code> يعيد رمي الإخفاقات المجمَّعة في <code dir="ltr">AssertionFailedException</code> واحدة، فيعمل المُدقِّق كتوكيد اختبار — بنفس تقرير النطاق المجمَّع.

والمساران يعبِّران عن نمطين مختلفين لاستهلاك النتيجة نفسها: <code dir="ltr">ToReportJson</code> يسلّم الصورة لمن يراقب، و<code dir="ltr">ThrowIfFailed</code> يسلّمها لمن يحكم. ووحدتهما في الشكل — نفس JSON — ليست مصادفة؛ فهي تعني أن لوحة المؤشرات التي تقرأ نتائج الاختبارات تقرأ نتائج الإنتاج بالقراءة ذاتها.

## 11.4 أحكام الرسوم بلا رمي

حين يكون الفحص مقارنة رسم كائني واحد، يعيد <code dir="ltr">EquivalencyEvaluation.Evaluate</code> الحكم مباشرة — بالمحرك نفسه ونصوص الفروق نفسها التي يطبعها <code dir="ltr">BeEquivalentTo</code>، وبلا أي رمي:

<div dir="ltr">

```csharp
var verdict = EquivalencyEvaluation.Evaluate(actualResponse, expectedResponse, o => o
    .WithDateTimeTolerance(TimeSpan.FromSeconds(2)));

if(!verdict.IsEquivalent) {
    logger.Warn(verdict.Message);                          // نص موحَّد بتنسيق ثابت
    attachments.Add("diff.json", verdict.ToReportJson());  // مسار ورسالة وexpected وactual لكل فرق
}
```

</div>

يحمل كل <code dir="ltr">EquivalencyDifference</code> المسار المنسَّق <code dir="ltr">Path</code> (<code dir="ltr">Address.City</code> أو <code dir="ltr">Tags[0]</code> أو <code dir="ltr">&lt;root&gt;</code>) والرسالة <code dir="ltr">Message</code> نفسها التي كان التوكيد سيطبعها والقيمتين المنسَّقتين <code dir="ltr">Expected</code>/<code dir="ltr">Actual</code> حيث يُبلِّغ موضع الفرق عنهما (الأعضاء المفقودة والمراجع الدورية مسار فقط). ترتيب الفروق يتبع المقارنة وهو جزء من العقد لأن CI يقرأ JSON.

وهنا تظهر فائدة أن المحرِّك واحد: حكم الإنتاج وفحص الاختبار يخرجان من الشفرة ذاتها، فلو اختلفا يومًا لكان الاختلاف في الطلب لا في الأداة. أما كون الترتيب عقدًا فقرار متعمَّد، لأن مقارنة النصوص في خط أنابيب تعتمد على موضع الفرق، ولو تبدّل الترتيب بلا سبب لاهتزت المقارنات واللوحات دون أن يتغير شيء حقيقي.

## 11.5 ما يبقى راميًا

ليست كل الأفعال قابلة للجمع، والسبب في طبيعتها لا في تصميم المدقِّق: بعض الأفعال لا معنى لها إلا بما تُعيده، فأين يذهب ما أعادته إذا كُتم الرمي؟ وفي مقدمة هذه العائلة <code dir="ltr">Throw*</code> التي تُعيد كائن استثناءات لمتابعة التفاصيل — نوعه ورسالته واستثناءه الداخلي — و<code dir="ltr">ContainSingle</code> الذي يُعيد العنصر الذي وُجد لتواصل التوكيد عليه. هذه الأفعال ترمي فورًا داخل كتلة المدقِّق و**توقف ما بعدها**، تمامًا كما تفعل داخل أي نطاق تجميع. فإما أن تُبقيها خارج كتلة التحقق، وإما أن تحرسها قبلها: تحقق من الشرط أولًا، ثم اطلبها في موضع لا يُفاجَأ فيه أحد بالتوقف.

والمعيار الفاصل واضح: كل فعل ينتهي إلى «نجح أو فشل» يُجمع، وكل فعل يحتاج قيمة راجعة يُستثنى بحكم الشكل. وليس في ذلك نقص في التصميم بل حدّ طبيعي: لا يمكن أن يحمل الإخفاق المجمَّع قيمةً ثالثة، والقيمة الراجعة هي جوهر هذه الأفعال لا زينتها. وما عدا ذلك — أفعال القيم والنصوص والمجموعات والترتيب والتكافؤ — يُجمع بلا استثناء، فيبقى المدقِّق واجهة واحدة شاملة لكل ما يُقاس بلا قيمة راجعة.

## 11.6 أين يقع هذا

ثلاث طبقات تجمع بلا رمي، ولكل عقد مختلف:

- <code dir="ltr">AssertionScope</code> يجمّع عند الخروج: تظهر الإخفاقات عند التخلص من النطاق كاستثناء واحد. الأفضل للاختبارات التي تريد الصورة الكاملة في فشل واحد.
- <code dir="ltr">SoftAssertions</code> يجمع عند الطلب: <code dir="ltr">Collect()</code> ثم أفعال ثم <code dir="ltr">ThenReport()</code> متى اخترت. بلا <code dir="ltr">using</code> إلزامي.
- <code dir="ltr">AssertionResult</code> لا يرمي أبدًا وهو الطرف المُوجَّه للإنتاج. المسار الافتراضي لم يتغيّر: خارج مُدقِّق أو نطاق، يرمي الإخفاق الأول فورًا.

لا شيء في الاختبارات الحالية يتغيّر.

والخريطة بسيطة إن رتّبتها بحسب **متى تريد النتيجة**: عند الخروج من النطاق، أو عند طلبك، أو الآن مباشرة. وكلها تستخدم نفس الأفعال ونفس الرسائل؛ فالاختيار بينها اختيار توقيت لا اختيار مكتبة.

## 11.7 خلاصة وتمرين

**الخلاصة:**

- **<code dir="ltr">AssertionResult.Create(...)</code> و<code dir="ltr">CreateAsync(...)</code>** ينفِّذان نفس أفعال <code dir="ltr">Should()</code> بلا رمي ويعيدان نتيجة هيكلية.
- **<code dir="ltr">IsSuccess</code> و<code dir="ltr">Failures</code>** لفحص النتيجة؛ **<code dir="ltr">ToReportJson()</code>** يسلسلها؛ **<code dir="ltr">ThrowIfFailed()</code>** يحوِّلها إلى إخفاق توكيد مجمَّع واحد.
- **الأفعال التي تُعيد قيمة — كعائلة <code dir="ltr">Throw*</code> و<code dir="ltr">ContainSingle</code> — لا تُجمَع**؛ ترمي فورًا وتوقف البقية، فأبقِها خارج كتل المدقِّق أو احرسها قبلها.
- **<code dir="ltr">EquivalencyEvaluation.Evaluate</code>** يمنحك نفس الحكم ونفس نصوص الفروق بلا رمي، للسجلات ولوحات المؤشرات.
- **ثلاث طبقات جمع، توقيت واحد:** نطاق، أو طلب، أو لا رمي — والأفعال والرسائل واحدة.

**تمرين:**

1. اكتب مُدقِّقًا يفحص ثلاث خصائص مستقلة لجسم، واجعل اثنتين تفشلان — وتأكد من ظهورهما في النتيجة بالترتيب.
2. سلْسل النتيجة بـ<code dir="ltr">ToReportJson()</code> وتحقَّق من المُخرَج بإعادة تحليله.
3. انقل نفس الكتلة إلى <code dir="ltr">AssertionResult.Create</code>، ثم حوِّلها إلى توكيد اختبار عبر <code dir="ltr">ThrowIfFailed()</code> ولاحظ الرسالة المجمَّعة.
