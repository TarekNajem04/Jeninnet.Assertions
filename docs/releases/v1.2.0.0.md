# Jeninnet.Assertions v1.2.0.0 — Ready for .NET 11 and C# 15

v1.2.0.0 adds first-class .NET 11 support without dropping a single older target. The core package now ships `net11.0` alongside `netstandard2.0`, `net6.0`, `net8.0`, and `net10.0`; every framework adapter gains the same target; and the solution builds with the .NET 11 SDK and C# 15.

The release also fixes a real behavior change in the new runtime: .NET 11 converts `double` to `decimal` through the exact binary expansion, which turned a caller's `0.01` tolerance into `0.0100000000000000002081668171` in failure messages. The fix keeps the number the caller wrote.

## Highlights

### .NET 11 assets, same API

The core package adds `lib/net11.0/Jeninnet.Assertions.dll` and the matching XML documentation. The MSTest, NUnit, xUnit, xUnit.v3, and TUnit adapters add `net11.0` assets as well. The analyzer stays on `netstandard2.0` because that is what Roslyn hosts load.

The public API is unchanged. A project that already references `Jeninnet.Assertions` can move to `net11.0` without changing a line of test code.

### C# 15

The repository now builds with `LangVersion` 15.0 on the .NET 11 SDK. The library still targets `netstandard2.0`, so the language version is a build-time choice, not a new consumer requirement.

### Decimal tolerances keep the value you wrote

This is the change users will notice. On .NET 10 and earlier, `(decimal)0.01d` produced `0.01m`. On .NET 11 it produces the exact binary expansion:

```text
0.0100000000000000002081668171
```

That value is correct as a representation of the `double`, but it is not the tolerance the caller intended. A failure message that reports it is harder to read and makes a simple `WithNumericTolerance(0.01)` look broken.

The equivalency engine now converts the tolerance through its shortest round-trippable representation before comparing decimal values. The comparison and the message both use `0.01`.

```csharp
actual.Should().BeEquivalentTo(expected, o => o.WithNumericTolerance(0.01));
```

### Timeout races do not leave a timer behind

`Task.WhenAny` with `Task.Delay` is still the only portable way to express a timeout on `netstandard2.0`. The delay is now paired with a `CancellationTokenSource` that is canceled as soon as the race settles. A passing assertion no longer leaves a timer counting down in the background.

```csharp
var completed = await Task.WhenAny(task, Task.Delay(timeout, cancellation.Token));
await cancellation.CancelAsync();
```

Older targets use `Cancel()`; .NET 8 and newer use `CancelAsync()`. The observable assertion behavior is unchanged.

Polling waits also clamp a negative remaining budget to zero. A slow runner can no longer turn the check-then-wait race into an `ArgumentOutOfRangeException` from `Task.Delay`.

### A clean quality gate

The SonarCloud gate is green:

- new-code coverage: 83.8% (threshold 80%)
- overall coverage: 80.1%
- duplicated lines: 0.3% (threshold 3%)
- reliability, security, and maintainability ratings: 1.0

The twelve open findings that were present on `main` are resolved. Lock fields now use `System.Threading.Lock` on .NET 9+ and `object` on older targets; duplicated message literals are named constants; the ten-field public `AssertionFailure` constructor keeps its shape for compatibility and carries a documented suppression. Two informational `IDE0028` suggestions remain and do not affect the gate.

## Compatibility

- Core package target frameworks: `netstandard2.0`, `net6.0`, `net8.0`, `net10.0`, `net11.0`.
- Adapter target frameworks: `net6.0`/`net8.0`/`net10.0`/`net11.0` (MSTest, NUnit, xUnit); `net8.0`/`net10.0`/`net11.0` (TUnit, xUnit.v3).
- The analyzer remains `netstandard2.0`.
- No public API changes and no intentional breaking changes.
- Package version is `1.2.0` on NuGet; the repository tag is `v1.2.0.0`.

## What this release is about

Supporting a new runtime is not only adding a target framework line. It means proving the old targets still build, running the suite on the new runtime, and noticing when the runtime changes the meaning of an existing expression. v1.2 does all three. The next release should keep the same rule: add the target, test it, and fix the behavior the new platform exposes.
